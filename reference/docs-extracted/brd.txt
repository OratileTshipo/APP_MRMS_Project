PART 1 — BUSINESS REQUIREMENTS DOCUMENT (BRD)
1.1 Business Context
DPWR North West currently tracks Annual Performance Plan (APP) delivery through a single Excel workbook spanning 17 directorate tabs, populated monthly by directorate staff and consolidated manually by the Directorate: Planning, Monitoring &amp; Evaluation (PM&amp;E). The Deputy Director: Monitoring has historically been the sole reviewer of every submitted report across all 17 directorates and 4 programmes — a single point of failure that delays consolidated reporting to the DMC (Departmental Management Committee) and EMC (Executive Management Committee), and creates a bottleneck at month-end and quarter-end review cycles.
APP-MRMS replaces this workbook with a governed, role-based Power Platform application that distributes review responsibility, enforces a consistent reporting structure, and produces auditable, queryable performance data for M&amp;E, DMC/EMC reporting, and eventual AGSA audit evidence.
1.2 Business Objectives
Eliminate the single-reviewer bottleneck by introducing a Supervisor tier that reviews Contributor submissions before escalation to the Deputy Director: M&amp;E.
Normalise 17 unstructured Excel tabs into a single relational data model (Directorate → Programme → Project → Activity → MonthlyReport) that supports filtering, roll-up, and trend reporting.
Provide real-time visibility of overdue, flagged, and pending reports to Programme Managers and M&amp;E without manual consolidation.
Establish an auditable review trail (who submitted, who reviewed, when, and why a report was rejected) sufficient to support internal control and audit requirements.
Reduce the reporting cycle time from current multi-week email/Excel consolidation to a same-day submission-to-review turnaround for the majority of reports.

3.7.5 Known Power Fx gotchas — carried forward from build notes
Distinct() returns a column named .Value, not .Result.
Choice columns require the .Value suffix (e.g. varUserRole.Value) when compared as text.
Collections must be built in dependency order — colProgrammeProgress and colMonthlyTrend must come after colReportsInScope, not before.
App.Formulas (Named Formulas) cannot reference Set() variables — role-scoping filters must live in OnVisible/OnStart, not Named Formulas.
Table({Title:"All"}) &amp; Programmes union pattern fails for a "clear filters" control — use a dedicated Clear Filters button instead.
SharePoint Lookup columns only expose .Id and .Value — always denormalize a flat label column onto the child list rather than chaining Lookups.

3.9 Security Architecture
Phase 1: role enforcement is in Power Fx (client-side visibility/filtering) — sufficient for an internal, trusted-user MVP but not a hard security boundary.
SharePoint list permissions should be tightened at minimum to: Contributors get Contribute (no Delete) on MonthlyReports scoped by their own items where possible via item-level permissions; broad list-level access otherwise, accepting the Phase 1 trade-off.
Administrator and DeputyDirectorME roles should be the only ones with Full Control / Design access to the underlying lists.
APP_Users.Role is the single source of truth for role — never hardcode role checks against email addresses in Power Fx.
Recommend Microsoft Entra ID group-based SharePoint permissions once user count grows, rather than per-user list permissions.
Phase 2 candidate: migrate from SharePoint lists to Dataverse for genuine row-level security (business units / security roles) if audit requirements tighten.
3.10 Error Handling
Wrap all Patch() calls with IfError() and surface a Notify() banner rather than a silent failure.
Validate required fields (PlannedAct, ProgressNarrative) client-side before enabling the Submit button, in addition to any list-level required-field enforcement.
On Patch failure, do not clear the form — preserve user input so nothing is lost on retry.
Log Patch failures to a lightweight local collection (colErrorLog) during Phase 1 for developer diagnosis; migrate to AuditLog-based capture once Phase 2 flows exist.
Guard all LookUp() calls against blank results with IsBlank() checks before dereferencing nested fields, to avoid delegation/runtime errors on first load.
IfError( Patch(MonthlyReports, ThisRecord, { Status: {Value:"Submitted"} }), Notify("Could not submit report. Please try again or contact support.", NotificationType.Error))
3.11 Performance Optimization
Denormalized label columns (DirectorateLabel, ProgrammeLabel, ActivityOwnerLabel, ProjectOwnerLabel) avoid chained LookUp/Lookup-of-Lookup calls in galleries — already applied consistently across Activities and MonthlyReports.
Use ClearCollect once on OnVisible rather than repeated Filter() calls directly on gallery Items — already your pattern for colReportsInScope.
Delegation: Filter/Search/SortByColumns on SharePoint sources delegate for standard operators (=, &lt;&gt;, StartsWith); GroupBy/AddColumns used for colProgrammeProgress/colMonthlyTrend run against the already-collected (non-delegated) set, which is safe once colReportsInScope itself was built with a delegable Filter.

Keep galleries' visible template controls minimal; hide non-essential fields at Small/Medium breakpoints per the responsive standard already on file.

3.13 Governance Recommendations
Maintain a single source-of-truth schema document (this TDS) and update it every time a list column changes in Studio — the v1→v2 drift that prompted this rebuild should not recur.
Reconcile the DirectorateLabel inconsistency (code vs. full name) before Phase 2 reporting is built on top of it — a Power BI measure built against one convention will silently miscount if the other list uses the other convention.
Decide and document whether Directorate/Programme text fields should be converted to Lookups, or intentionally kept as text with validation — don't leave it ambiguous.
Establish a data retention/archival rule for MonthlyReports once multiple financial years accumulate (the FinancialYear choice field already supports this).
Define who owns the AuditLog/Notifications/ReportComments write-paths in Phase 2 — recommend Power Automate rather than Canvas App Patch calls, so the audit trail is not bypassable by the app itself.
Before onboarding all 17 directorates, pilot with 2–3 (as already done with ICTM) and capture friction points in Approval Queue and rejection flow specifically, since these are new to end users vs. the old Excel process.

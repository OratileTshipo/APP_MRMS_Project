0. Executive Summary &amp; Review of Existing Project Material
This pack was developed after reviewing the three documents already in the project workspace: the live APP Implementation Plan 2026/27 workbook (17 directorate sheets – Communications, Legal Services, ICT, Strategic Planning M&amp;E, HRM, HRD, Finance, SCM, CFO, Risk &amp; Internal Control, Special Programmes, Security Services, and Programmes 2A, 2B, 3 and 4), the draft Technical Design Specification, and the draft APP Reporting System FDS.
Three findings from that review shaped this design:
The real-world data is naturally hierarchical and repeats a fixed pattern across every sheet: Directorate/Programme → Priority/Challenge &amp; Key Deliverable → Activities → a recurring April-to-March pair of “Activities / Progress” columns. This maps directly onto a Programme → Project → Activity → Monthly Report data model, which is the model used throughout this document.
The existing draft TDS/FDS used a 3-tier role model (User, Manager, M&amp;E) and a single-level approval. The brief for this engagement specifies four roles — Administrator, Programme Manager, Supervisor, Contributor — with explicit KPI tracking, progress indicators, threaded comments, full audit trail and approval history. This pack supersedes the earlier draft and extends it accordingly, while keeping the same SharePoint-first, low-code delivery philosophy.
The earlier TDS already flagged that SharePoint list attachments are a weak substitute for a proper evidence repository. This pack carries that recommendation forward as a firm design decision (Section 4 and Section 15) and adds Microsoft Forms as a lightweight, low-bandwidth field-capture channel — important given several Activities in the workbook are executed at district and sub-district level with variable connectivity (e.g. Ganyesa, Sannieshof, Atamelang, Morokweng).
The remainder of this document is organised as fifteen numbered deliverables, in the order : BRD, FDS, TDS, SharePoint data model, lookup relationships, Power Apps screens, container hierarchy, responsive formulas, Power Fx formulas, Power Automate flows, security architecture, error handling, performance optimisation, deployment strategy and governance.

1. Business Requirements Document (BRD)
1.1 Background
APP (Annual Performance Plan) implementation is currently tracked in a single, very wide Excel workbook with one sheet per directorate/programme. Each row carries a Priority/Challenge, a Key Deliverable, an Annual Target, a Budget reference, and 24 paired “Activities / Progress” columns running April through March. Progress narratives are typed directly into cells by directors and submitted by email or shared drive for consolidation by Strategic Planning, Monitoring &amp; Evaluation (SP M&amp;E) ahead of DMC, EMC and Lekgotla reporting cycles.
This approach is functionally adequate but operationally fragile: there is no single source of truth, no enforced workflow, no version history, no automatic reminders, and no audit trail — all of which become material weaknesses during AGSA audit engagements where evidence of timely review, approval and corrective action is itself an audit point (the workbook contains multiple AGSA-related corrective action items).
1.2 Business Objectives
Replace the spreadsheet-based process with a governed, role-based digital workflow.
Establish one authoritative record per Programme → Project → Activity → Monthly Report, replacing manual consolidation.
Enforce a draft → submit → review → approve/reject cycle with full audit trail and approval history.
Provide real-time dashboards (KPI attainment, progress against Annual Target, overdue items) for DMC/EMC and Lekgotla preparation.
Reduce administrative effort spent consolidating progress narratives manually each month.
Capture evidence (POEs) against each monthly report in a governed, versioned evidence repository.
Enable low-connectivity field/district reporting via Microsoft Forms as an alternate capture channel.
1.3 Scope
In Scope
Programme, Project and Activity master data administration.
Monthly progress capture, drafting, submission and multi-stage approval.
KPI/target definition and automatic progress-indicator calculation.
Attachments/evidence, threaded comments, notifications, audit trail and approval history.
Role-based Power Apps Canvas application for all four user roles.
Power BI dashboards for executive/oversight reporting.
Microsoft Forms-based lightweight capture for low-connectivity contributors.
Out of Scope (Phase 1)
Integration with financial systems (BAS, Reapatala) – budget fields remain free text/reference in Phase 1, recommended as a Phase 2 integration.
HR/Persal integration for organisational hierarchy – Phase 1 uses Entra ID groups and a Users list maintained by Administrators.
Public-facing access – the system is for internal departmental users only.

1.6 Assumptions &amp; Constraints
The Department holds Microsoft 365 (SharePoint Online, Power Apps/Power Automate per-user or per-app, Power BI Pro) licensing, or will procure it.
Entra ID (Azure AD) is the system of record for user accounts; departmental security groups exist or will be created per role/Programme.
SharePoint Online list view threshold (5,000 items per non-indexed view) and the practical comfort ceiling for canvas-app-bound lists (broadly tens of thousands of rows with indexing/delegation) are accepted constraints for Phase 1; Dataverse migration is the recommended Phase 2 path if volumes or row-level security needs grow (see Section 15).
District/sub-district connectivity is inconsistent; the design must tolerate intermittent connectivity (Forms + offline-tolerant patterns).
Financial year runs April – March, consistent with the existing workbook.

2.1 User Roles &amp; Responsibilities

2.2 Functional Requirements
2.2.1 User &amp; Security Management (FR-1xx)
FR-101 Administrators can create, edit, deactivate Users and assign Role and Programme/Project scope.
FR-102 The system shall map Entra ID security groups to in-app roles at sign-in.
FR-103 The system shall prevent a user from acting outside their assigned role or assigned Programme/Project scope.
2.2.2 Programme Management (FR-2xx)
FR-201 Administrators can create/edit/archive Programmes (e.g. Programme 1–4, or Chief Directorate groupings).
FR-202 Each Programme has an accountable Programme Manager (Person field) and an Active flag.
FR-203 Programme Managers can view, but not delete, all Projects under their Programme.
2.2.3 Project Management (FR-3xx)
FR-301 Administrators (and Programme Managers, for their own Programme) can create/edit Projects, equivalent to a Key Deliverable / Priority-Challenge record, with Annual Target, Reference, Budget, Start/Completion Date and Status.
FR-302 Each Project belongs to exactly one Programme (lookup) and may contain many Activities.
FR-303 Projects carry one or more KPI/Target definitions used for progress-indicator calculation.
2.2.4 Activity Management (FR-4xx)
FR-401 Administrators/Supervisors can create/edit Activities within a Project, set Frequency (Monthly/Quarterly/Annual), assign an Owner (Contributor) and define the reporting calendar (Start/End Date, due-day-of-month).
FR-402 Activities can be deactivated without deleting historical reports.
2.2.5 Monthly Reporting, Drafts &amp; Submission (FR-5xx)
FR-501 Contributors see a personal ‘My Activities’ list filtered to items due in the current/selected reporting period.
FR-502 Contributors can capture Planned Activity, Progress Narrative and Percentage Complete, and save as Draft repeatedly without triggering workflow.
FR-503 Submitting a report locks the Contributor-editable fields and sets Status = Submitted, recording SubmittedBy and SubmissionDate.
FR-504 The system shall maintain one MonthlyReport record per Activity per ReportingMonth per FinancialYear, with a Version number incremented on every resubmission.
2.2.6 Approval Workflow &amp; Rejection (FR-6xx)
FR-601 Submitted reports appear in the assigned Supervisor’s Approval Queue.
FR-602 Supervisors can Approve, Reject (mandatory comment) or Return for Correction (mandatory comment).
FR-603 Rejected/Returned reports revert to the Contributor as an editable draft, retaining the prior narrative and the Supervisor's comment for context.
FR-604 Approved reports are visible read-only to the Contributor, Supervisor and the Project’s Programme Manager.
FR-605 Programme Managers can perform an escalation-level review/override on any report within their Programme, recorded distinctly from Supervisor approval.
2.2.7 Attachments &amp; Comments (FR-7xx)
FR-701 Users can attach one or more evidence files to a monthly report, stored in a governed Evidence Library (not raw list attachments).
FR-702 Any role with visibility of a report can add a threaded comment; comments are timestamped and attributed.
FR-703 Comment authors and the report owner are notified of new comments.
2.2.8 KPI Tracking &amp; Progress Indicators (FR-8xx)
FR-801 Each Project displays a calculated progress indicator (RAG status + percentage) derived from its Activities’ latest approved Percentage Complete weighted against the Annual Target.
FR-802 Programme-level KPI roll-ups aggregate all Projects within a Programme.
FR-803 RAG thresholds (Red/Amber/Green) are configurable by Administrators per KPI definition.
2.2.9 Dashboards, Search &amp; Filtering (FR-9xx)
FR-901 The in-app Home Dashboard shows role-appropriate cards (counts) and charts (monthly trend, Programme performance, overdue items).
FR-902 A Power BI dashboard provides executive-level, cross-Programme reporting, refreshed on a schedule.
FR-903 Users can search by free text (Activity/Project title, keyword in narrative) and filter by Financial Year, Quarter, Month, Programme, Project, Status and Owner.
2.2.10 Notifications (FR-10xx)
FR-1001 The system sends a reminder ahead of the monthly due date to each Contributor with an outstanding Activity.
FR-1002 The system notifies the Supervisor on submission, the Contributor on approval/rejection, and the Programme Manager on escalation.
FR-1003 The system escalates overdue (unsubmitted) reports automatically after a configurable grace period, first to the Supervisor, then to the Programme Manager.
2.2.11 Audit Trail &amp; Approval History (FR-11xx)
FR-1101 Every create, edit and status transition is written to an append-only Audit Log capturing actor, timestamp, entity, field-level change (where applicable) and reason/comment.
FR-1102 Each MonthlyReport exposes a chronological Approval History (submit → review → decision → resubmit) independent of the generic audit log, for quick on-screen review.
2.2.12 Security (FR-12xx)
FR-1201 Access to screens, records and actions is governed by role and Programme/Project assignment, enforced in both the application layer and the data layer.
2.3 Core Process Flow
Monthly Reporting Lifecycle:
Contributor opens an assigned Activity for the current reporting period and captures progress; saves as Draft (repeatable, no workflow triggered).
Contributor submits; Status → Submitted; Supervisor notified; Audit Log entry written.
Supervisor reviews. If Approved → Status → Approved; Contributor notified; Project/Programme KPI roll-up recalculated.
If Rejected/Returned → Status → Rejected with mandatory comment; Contributor notified; record becomes editable again; Version increments on resubmission; loop to step 1.
Programme Manager may, at any time, open an escalation review on a report within their Programme (e.g. disputed rejection, audit follow-up), recorded as a distinct Approval History entry.
On the due date + grace period, any Activity without a Submitted/Approved report for the period triggers the Overdue Escalation flow.

SharePoint → Power Automate → Outlook/Teams: list-triggered flows for reminders, escalations and approval notifications.

5.2 Cascading Selection in Power Apps
SharePoint Lookup columns do not natively cascade. Dependent dropdowns (Programme → Project → Activity) are implemented in Power Apps using chained Filter() calls against locally cached collections, refreshed at App.OnStart and on pull-to-refresh:
// Project dropdown, filtered by the selected Programme
Items: Filter(colProjects, Programme.Id = ddProgramme.Selected.Id)
 
// Activity dropdown, filtered by the selected Project
Items: Filter(colActivities, Project.Id = ddProject.Selected.Id, Active = true)
Lookup columns are configured as single-value (not multi-value) throughout, since SharePoint multi-value lookups are non-delegable and degrade gallery performance at scale; Person fields follow the same single-value rule except where a field is explicitly designed for multiple reviewers (none in this model).

10.1 Error-Resilient Flow Pattern (applies to all flows above)
Trigger
 -&gt; Scope: "Try"
 - main actions (Patch/Create/Send notification)
 -&gt; Scope: "Catch" [Configure run after: Try has failed, has timed out]
 - Compose error details (status code, message)
 - Send email to Power Platform Administrator distribution list
 - Create AuditLog entry: Action = "FlowError"
 -&gt; Scope: "Finally" [Configure run after: Try succeeded OR Catch has run]
 - Terminate (Succeeded / Failed, based on which scope ran)

12. Error Handling
12.1 Power Apps
All Patch/Collect/Remove calls are wrapped in IfError(), surfacing FirstError.Message via Notify(NotificationType.Error) rather than failing silently.
A lightweight client-side ErrorLog collection captures the error, screen and control context, and is flushed to a small SharePoint ErrorLog list on a timer/OnHidden, giving Administrators visibility into recurring UI errors without needing user-reported tickets.
Form-level validation (required fields, percentage range 0–100, date logic) runs before Submit is enabled, using a single varFormIsValid boolean checked by the Submit button's DisplayMode.
Set(varFormIsValid,
 Not(IsBlank(txtProgress.Text)) And
 sldComplete.Value &gt;= 0 And sldComplete.Value &lt;= 100
);
btnSubmit.DisplayMode = If(varFormIsValid, DisplayMode.Edit, DisplayMode.Disabled);
12.2 Power Automate
Every flow follows the Try/Catch/Finally scope pattern shown in Section 10.1, using ‘Configure run after’ so failures are caught rather than aborting silently.
Retry policies are set on all SharePoint/Outlook actions (default 4 retries, exponential interval) to absorb transient throttling (HTTP 429) without manual intervention.
A dedicated Power Platform Administrator distribution list receives a structured error email (flow name, run ID, error message, affected item) on any Catch branch execution, and a corresponding AuditLog ‘FlowError’ entry is written for traceability.
Long-running scheduled flows (Overdue Escalation, Annual Consolidation) include a Timeout setting on the main Scope to prevent runaway executions against a growing dataset.

13. Performance Optimization
13.1 Delegation
All gallery/search queries use delegable functions – Filter, Search, SortByColumn, LookUp on indexed columns – against the SharePoint connector's supported delegation set.
Non-delegable operations (e.g. multi-condition aggregation across lookups, as in the KPI roll-up in Section 9.5) are deliberately scoped to a single Project at a time so the underlying Filter() stays within the non-delegated row limit, rather than ever running across the full MonthlyReports list.
CountRows()/Sum() used for dashboard cards operate against pre-filtered, period-scoped collections (e.g. the current month) rather than the entire history.
13.2 Indexing
The following columns are explicitly indexed to keep filtered views and Power Fx delegation under the SharePoint 5,000-item list view threshold as data accumulates over multiple financial years:
MonthlyReports: Activity, Status, FinancialYear, ReportingMonth
Activities: Project, Owner
Projects: Programme
AuditLog: ActionDate, EntityType
13.3 Caching &amp; Collection Strategy
Slow-changing reference data (Programmes, Projects, Activities, KPIDefinitions) is loaded once into collections at App.OnStart and refreshed on a manual pull-to-refresh, avoiding repeated round trips on every screen visit.
Concurrent() is used at OnStart to load independent collections in parallel rather than sequentially.
Galleries are scoped to the current reporting period by default, with an explicit ‘Load more / change period’ filter rather than loading full history.
13.4 List &amp; UI Scaling
Each transactional list carries an indexed default view filtered to the current/recent financial year to avoid the 5,000-item list view threshold being hit on the default view.
Older financial years are moved to year-stamped archive lists by the Annual Consolidation flow (Section 10), keeping the live MonthlyReports list lean for day-to-day delegation performance.
Galleries implement simple page-based loading (Set(varPage, varPage+1) with First()/Skip() over a locally sorted collection) rather than rendering unbounded result sets.
Attachment/evidence images are compressed client-side (Camera/Attachments control quality setting) before upload to reduce both upload time on low-bandwidth district connections and Evidence Library storage growth.
13.5 Power BI
The Power BI dataset uses Import mode with a scheduled refresh (e.g. every 4 hours) rather than DirectQuery against SharePoint, which is not well suited to high user concurrency.
Aggregation tables (pre-summarised by Programme/Project/Month) are built in Power Query to keep visual-level queries fast regardless of underlying row growth.

14. Deployment Strategy
14.1 Application Lifecycle Management (ALM)
All components (Canvas App, flows, environment variables, connection references) are packaged as a single Power Platform Solution, developed as Unmanaged in the Development environment.
Power Platform CLI (pac cli) and Power Platform Pipelines (or an Azure DevOps/GitHub Actions pipeline) export the solution, convert it to source-controlled, unpacked components, and build a Managed Solution for downstream environments.
SharePoint site URL and key list GUIDs are abstracted as Environment Variables / Connection References inside the solution so the same managed solution can be imported into Test and Production without manual rewiring.
14.2 Release Pipeline
Build &amp; unit test in Development (unmanaged).
Export solution → source control (Git) → build pipeline produces a versioned Managed Solution.
Import Managed Solution into Test/UAT; run a structured UAT script per role (Administrator, Programme Manager, Supervisor, Contributor); load representative sample data (a subset of the existing APP Implementation Plan workbook).
Obtain formal UAT sign-off from SP M&amp;E and at least one Programme Manager per Programme.
Import Managed Solution into Production during an agreed change window; run a smoke test script.
One-time historical data migration: a Power Automate/Power Query import maps the existing workbook's Directorate sheets and monthly Activity/Progress columns into Programmes, Projects, Activities and historical MonthlyReports (Status = Approved, ReviewDate backdated for audit continuity).
Hypercare period (first full reporting month) with daily monitoring of flow run history and user-reported issues before handover to standard support.
14.3 Rollback
The previous Managed Solution version is retained and can be re-imported (the Power Platform preserves solution history); SharePoint list schema changes are additive-only during the pilot cycle to avoid destructive rollback scenarios.
14.4 Rollout Approach
A phased rollout is recommended: pilot with a single Programme (suggested: Programme 4 – Community-Based Programme, given its already well-structured monthly KPI narrative in the existing workbook) for one full reporting cycle, then onboard the remaining Programmes and Directorate sheets in two further tranches.

15. Governance Recommendations
15.1 Centre of Excellence (CoE)
Adopt the Microsoft Power Platform CoE Starter Kit to maintain an inventory of apps/flows, monitor DLP compliance, and flag orphaned or unmanaged solutions across the tenant.
Establish a small Power Platform governance group (Administrator + IT representative + one Programme Manager) to review schema changes and new feature requests on a quarterly cadence.
15.2 Data Governance
Move from list-attachment-based evidence to the governed EvidenceLibrary document library (Section 4.6) – this is a firm recommendation carried forward from the existing draft TDS, not optional, given audit-evidence requirements.
Apply SharePoint retention labels/policies to MonthlyReports, AuditLog and EvidenceLibrary aligned to public-sector records retention rules (minimum 5 years).
Enable recycle-bin and versioning on all lists/libraries; consider a third-party backup solution (e.g. AvePoint, Veeam) for point-in-time recovery beyond the native 93-day SharePoint recycle bin.
15.3 Licensing &amp; Access Governance
Use Per-App plans for Contributors (high volume, single-app usage) and Per-User plans for Administrators/Programme Managers/Supervisors who may need broader Power Platform access.
Quarterly access review: Administrators reconcile the Users list and Entra ID group membership against current organograms, removing access for staff who have exited (the workbook itself shows meaningful staff turnover – retirements, resignations – that must be reflected promptly in system access).
15.4 Naming, Documentation &amp; Change Control
Enforce the naming conventions in Section 3.4 across all environments via the CoE Starter Kit's naming policy checks.
Maintain this document pack (BRD/FDS/TDS) as the single source of truth, version-controlled alongside the exported solution in Git; any schema or workflow change ships with a corresponding documentation update.
Require change-board sign-off for any change to the approval workflow, security model, or KPI calculation logic, given their audit relevance.
15.5 Roadmap Beyond Phase 1
Dataverse migration: once data volumes, concurrent users or row-level security needs exceed comfortable SharePoint-list scale, migrate the data layer to Dataverse for native Security Roles, Business Units and Row-Level Security, while keeping the same Power Apps/Power Automate/Power BI front end.
Financial system integration (BAS/Reapatala) to replace free-text Budget fields with live expenditure data, closing the loop between APP commitments and actual spend referenced throughout the existing workbook.
Power BI paginated reports for formal, print-ready DMC/EMC/Lekgotla packs generated directly from the same governed dataset.
